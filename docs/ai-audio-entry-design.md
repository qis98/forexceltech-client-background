# 智能录音录入模块设计方案

## 1. 文档状态

- 文档日期：2026-06-20
- 当前状态：已进入 MVP 开发；本文继续作为智能录入模块的产品和技术设计记录
- 目标模块名称：智能录入
- 目标用户：销售人员、客户经理、项目负责人

本模块用于从销售拜访、电话沟通或会议录音中提取客户信息，并生成客户、联系人、拜访记录的待确认草稿。

## 2. 核心结论

当前 MVP 调整为“用户粘贴文字稿 + Ollama 本地模型结构化抽取 + 人工确认入库”的方案。

原因：

- 产品核心价值在于从文字段落中提取客户、联系人和拜访记录，而不是录音转写。
- 更符合“本地优先、数据不出本地”的产品定位。
- 可先用 Ollama 调用本机 `qwen3:8b` 快速评估抽取质量。
- 录音转文字可先交给手机、会议软件或其他工具完成，再把文字稿粘贴进软件。

第一版不建议让本地模型直接写入正式数据。模型结果必须先进入“待确认草稿”，由用户确认或修改后，再写入客户、联系人、拜访记录。

实际销售录音中经常不会完整说出客户全称，甚至只会出现“李经理”“王工”“上次那条线”这类上下文信息。因此客户归属不能只依赖模型判断。

当前产品策略：

- 人工预关联优先于 AI/规则推测。
- 用户可在生成草稿前选择已有客户。
- 用户可在生成草稿前选择已有联系人；联系人会自动反推所属客户。
- 已预关联的客户或联系人用于重复识别和合并判断，不应再次创建同名正式数据。
- 如果录音内容没有足够信息判断客户或联系人，草稿仍保留字段，并显示“未知，待人为补充”。

## 3. 用户补充规则

如果录音或文字稿中没有可以关联的客户信息，或者缺少必填关键信息，界面仍然必须显示对应字段。

字段值统一显示为：

```text
未知，待人为补充
```

这个规则适用于所有 AI 抽取结果：

- 不隐藏缺失字段。
- 不因为字段缺失而丢弃整条草稿。
- 不用空白值冒充已识别结果。
- 必填字段缺失时，允许保存为草稿，但不允许直接确认入库。
- 用户补齐必填字段后，才能写入正式客户、联系人或拜访记录。

示例：

| 字段 | AI 识别结果 |
| --- | --- |
| 客户名称 | 未知，待人为补充 |
| 联系人姓名 | 王经理 |
| 联系人职位 | 未知，待人为补充 |
| 拜访主题 | 新产线设备需求沟通 |
| 下一步动作 | 下周发送方案报价 |

## 4. 目标业务价值

当前客户资料维护依赖人工录入，销售拜访后容易遗漏联系人、客户态度、下一步动作和需求细节。

智能录入模块要解决：

- 降低拜访后手工录入成本。
- 把口头沟通沉淀成结构化客户资产。
- 避免只保存一段录音，后续无法检索和复盘。
- 帮助销售快速补齐客户、联系人和拜访记录。

## 5. 第一版范围

当前 MVP 只做“粘贴文字稿后生成待确认草稿”。

包含：

- 粘贴本地文字稿。
- 调用 Ollama 本地模型从文字稿中抽取结构化信息。
- Ollama 不可用时回退本地规则。
- 展示客户、联系人、拜访记录草稿。
- 标记未知字段为“未知，待人为补充”。
- 支持用户编辑草稿。
- 支持关联已有客户。
- 支持关联已有联系人。
- 支持确认后写入正式数据库。

不包含：

- 实时录音。
- 实时字幕。
- 多人说话人精确识别。
- 打包内置模型文件。
- 自动无确认入库。
- 自动拨打电话或接入通讯软件。

## 6. 推荐用户流程

```text
进入智能录入
 -> 用户可预关联已有客户或联系人
 -> 用户粘贴文字稿
 -> 系统生成结构化草稿
 -> 用户检查未知字段
 -> 用户关联已有客户或创建新客户
 -> 用户关联已有联系人或创建新联系人
 -> 用户修改拜访记录
 -> 用户确认写入数据库
```

确认入库前必须展示摘要：

- 将新增几个客户。
- 将新增几个联系人。
- 将新增几条拜访记录。
- 将更新哪些已有客户或联系人。
- 哪些必填字段仍为“未知，待人为补充”。

确认入库应支持两种粒度：

- 单张草稿确认：客户、每张联系人草稿、拜访记录各自提供独立写入按钮。
- 全部确认：页面底部提供全局按钮，按客户、所有联系人、拜访记录的顺序写入。

依赖规则：

- 客户是联系人和拜访记录的关联主体。
- 预关联客户优先于模型识别出的客户。
- 预关联联系人优先于模型识别出的联系人，并自动带出其所属客户。
- 更换预关联客户时，如果已选择联系人不属于该客户，应清空联系人选择，避免跨客户错误关联。
- 联系人写入前必须先有关联客户，关联客户可以是已匹配的已有客户，也可以是刚写入的客户草稿。
- 拜访记录写入前必须先有关联客户；如果多张联系人草稿已写入，则自动作为拜访参与人关联。
- 已写入的草稿需要显示已写入状态，并避免重复点击造成重复数据。

## 7. 信息抽取对象

### 7.1 客户草稿

字段建议：

- 客户名称
- 客户简称
- 行业
- 区域
- 地址
- 电话
- 网站
- 客户状态
- 重要等级
- 负责人
- 标签
- 客户背景
- 备注

必填建议：

- 客户名称

如果客户名称未知，则客户草稿仍显示，但不能直接创建正式客户。

### 7.2 联系人草稿

一段文字稿可能包含多位关键人，联系人草稿必须支持数组结构。每位关键人应生成独立草稿，例如“联系人草稿 1”“联系人草稿 2”。不要因为第一位联系人已经识别成功就丢弃后续联系人。

字段建议：

- 所属客户
- 姓名
- 性别
- 部门
- 职位
- 电话
- 邮箱
- 微信
- 学历
- 专业背景
- 过往任职经历
- 关系状态
- 沟通偏好
- 决策角色
- 影响力
- 个人兴趣
- 下次可提及话题
- 备注

必填建议：

- 所属客户
- 姓名

如果联系人姓名未知，则联系人草稿仍显示，但不能直接创建正式联系人。

### 7.3 拜访记录草稿

字段建议：

- 所属客户
- 拜访类型
- 拜访主题
- 发生时间
- 地点
- 参与联系人
- 摘要
- 详细内容
- 客户态度
- 下一步动作
- 记录人

必填建议：

- 所属客户
- 拜访主题
- 发生时间

如果所属客户未知，仍保留拜访记录草稿，并显示“未知，待人为补充”。

## 8. 匹配和去重规则

核心原则：

- 人工选择的客户或联系人优先级最高。
- AI/规则匹配只作为建议，不应在用户未确认时自动合并或覆盖正式数据。
- 如果用户预关联已有客户，客户草稿只作为复核和补充，不重复创建客户。
- 如果用户未预关联客户，但系统发现疑似已有客户，必须展示客户匹配确认区，由用户选择“使用已有客户”或“按草稿新建客户”。
- 如果用户预关联已有联系人，联系人草稿只作为复核和补充，不重复创建联系人。
- 拜访记录可以在已有客户和联系人下新增，因为同一客户同一联系人可以有多次真实沟通。

### 8.1 客户匹配

优先匹配：

- 用户预关联的客户。
- 客户全称完全一致。
- 客户简称完全一致。
- 客户名称模糊匹配。
- 行业和区域辅助判断。

客户名称模糊匹配只能作为候选提示，不能静默合并客户。没有人工预关联客户时，即使命中候选客户，也必须让用户确认后再写入。

如果匹配结果不唯一，必须让用户选择。

### 8.2 联系人匹配

优先匹配：

- 用户预关联的联系人。
- 同一客户下姓名完全一致。
- 同一客户下姓名加职位相似。
- 电话、邮箱、微信完全一致。

如果只出现“王总”“李经理”这类称呼，建议生成联系人草稿，但标记姓名或职位可信度低。

### 8.3 拜访记录去重

优先判断：

- 同一客户。
- 同一联系人或参与人高度重合。
- 发生时间接近。
- 拜访主题相似。
- 摘要内容相似。

如果疑似重复，应提示用户选择“合并到已有记录”或“仍创建新记录”。

当前 MVP 已实现客户/联系人层面的预关联去重，并在智能录入写入拜访记录前加入疑似重复提示。

第一版拜访记录重复提示规则：

- 只检查智能录入生成的拜访记录，不影响客户详情中的手工新增。
- 先限定同一客户。
- 如果已有关联联系人，则要求同一联系人参与。
- 时间差在 24 小时内优先命中，72 小时内作为弱命中。
- 拜访主题按字符和相邻字符片段做相似度判断。
- 命中后提示用户选择“合并到已有记录”或“仍创建新记录”。
- 选择合并时，显示已有记录和当前草稿的字段差异。
- 选择合并时，默认保留已有记录的主题、发生时间、地点、客户态度、下一步动作和记录人。
- 选择合并时，将新草稿的摘要和详细内容补充到已有记录，并合并参与联系人。
- 不做静默覆盖，不自动删除任何记录。

2026-06-20 场景测试发现，早期合并实现会更新部分已有记录字段，例如主题、摘要、下一步动作等。现已调整为应用内合并确认弹窗和保守合并策略。后续增强可继续增加多候选列表和字段级勾选覆盖能力。

## 9. AI 结果可信度

每个草稿对象建议带整体可信度：

- 高：字段明确，客户和联系人可匹配。
- 中：主要字段明确，但部分字段缺失或存在歧义。
- 低：客户或必填字段缺失，需要人工补充。

每个字段也建议保留来源片段，方便用户回看 AI 为什么这样填。

示例：

| 字段 | 值 | 来源片段 | 可信度 |
| --- | --- | --- | --- |
| 联系人职位 | 采购经理 | “李经理这边主要负责采购” | 中 |
| 下一步动作 | 下周发送方案报价 | “你们下周把方案和报价发过来” | 高 |

## 10. 技术路线对比

### 10.1 方案 A：联网语音转文字 + 联网大模型抽取

流程：

```text
录音文件 -> 语音转文字 API -> 文字稿 -> 大模型结构化抽取 -> 草稿确认页
```

难度：中等偏高。

优点：

- 准确率最高。
- 开发速度最快。
- 安装包体积小。
- 对用户电脑性能要求低。

缺点：

- 需要联网。
- 需要 API Key。
- 有调用成本。
- 录音或文字稿会发送到第三方服务。

已暂缓。当前产品优先验证本地文字抽取价值。

### 10.2 方案 B：本地语音转文字 + 联网大模型抽取

流程：

```text
录音文件 -> 本地 Whisper/whisper.cpp 转文字 -> 大模型结构化抽取 -> 草稿确认页
```

难度：中高。

优点：

- 原始录音不上传。
- 只上传文字稿，隐私风险低于方案 A。
- 仍可使用云端大模型保证抽取效果。

缺点：

- 本地转写速度依赖电脑性能。
- 需要打包或引导安装本地模型。
- 安装包和部署复杂度增加。

适合第二阶段评估。

### 10.3 方案 C：完全本地语音转文字 + 本地大模型抽取

流程：

```text
录音文件 -> 本地转写 -> 本地大模型抽取 -> 草稿确认页
```

难度：高。

优点：

- 离线可用。
- 数据隐私最好。
- 没有云端 API 调用成本。

缺点：

- 模型文件大。
- 用户电脑性能差异明显。
- 本地大模型抽取准确率和稳定性需要大量调试。
- 打包、升级、售后复杂。

不建议第一版使用。

### 10.4 方案 D：先支持粘贴文字稿 + 本地模型抽取

流程：

```text
用户用手机、会议软件或第三方工具转写 -> 粘贴文字稿 -> Ollama 本地模型抽取 -> 草稿确认页
```

难度：中。

优点：

- 不需要第一时间处理音频格式。
- 可以先验证结构化抽取和草稿确认流程。
- 可作为智能录入模块的低风险起步版本。

缺点：

- 不能完整满足“从录音中提取信息”的目标。
- 用户需要先自己完成转写。

可作为开发前置版本或内部测试入口。

## 11. 建议技术方案

当前 MVP 建议：

- 入口名称：智能录入。
- 支持粘贴文字稿。
- 结构化抽取优先使用 Ollama 本地模型。
- 默认模型为 `qwen3:8b`。
- Ollama 不可用或输出不合规时回退本地规则。
- 设置页支持“仅本地规则”和“Ollama 本地模型”两种模式。
- 设置页支持配置 Ollama 服务地址和模型名称。
- 所有 AI 结果先保存为本地草稿。
- 确认入库前必须由用户审核。

第二阶段再评估：

- 本地 whisper.cpp 转写。
- 说话人分离。
- 实时录音和实时转写。

相关参考：

- Ollama Structured Outputs 文档：https://docs.ollama.com/capabilities/structured-outputs
- whisper.cpp 项目：https://github.com/ggml-org/whisper.cpp

## 12. 数据保存建议

遵循当前项目规则，所有文件继续放在 D 盘。

建议新增目录：

```text
D:\FOREXCELTECHClientManager\transcripts
D:\FOREXCELTECHClientManager\ai-drafts
D:\FOREXCELTECHClientManager\config.json
```

建议用途：

- `transcripts`：后续如接入转写功能，用于保存转写文字稿。
- `ai-drafts`：保存 AI 抽取草稿、来源片段和处理日志。
- `config.json`：保存本地模型配置，包括 Ollama 服务地址和模型名称。

隐私策略建议：

- 当前 MVP 不上传文字稿到外部 AI 服务。
- 支持用户选择是否保留原始录音副本。
- 支持删除某次智能录入任务的录音、文字稿和草稿。
- 当前 MVP 不需要 API Key。

## 14. 交互设计建议

智能录入页面建议分为四块：

- 上传区：选择录音文件，显示文件名、大小、时长。
- 预关联区：选择已有客户或联系人，用于提高归属判断和去重准确率。
- 文字稿区：展示语音转文字结果，允许人工修正。
- 草稿区：按客户、联系人、拜访记录分组展示 AI 结果；联系人允许展示多张草稿。
- 入库确认区：展示将新增或更新的数据，并提示未知必填字段。

草稿字段状态建议：

- 已识别：正常显示字段值。
- 未识别：显示“未知，待人为补充”。
- 低可信：显示黄色提示。
- 疑似重复：提示选择已有记录或新建记录。

## 15. 验收标准

第一版完成后至少满足：

- 可上传一段录音并生成文字稿。
- 可从文字稿生成至少一条拜访记录草稿。
- 可从文字稿生成客户和联系人草稿；当文字稿出现多位关键人时，可生成多张联系人草稿。
- 缺失字段显示“未知，待人为补充”。
- 必填字段缺失时不能直接确认入库。
- 用户补齐必填字段后可写入正式数据库。
- 能关联已有客户，避免重复创建。
- AI 结果写入前有明确确认步骤。
- 处理失败时有可理解的错误提示。
- `docs/help.md` 在功能上线时同步更新。

## 16. 主要风险

- 录音质量差导致转写错误。
- 会议中出现多个客户，AI 分配错误。
- 只用称呼而没有客户名，无法自动关联。
- 大模型把推测当事实填入字段。
- 用户误确认错误草稿，污染正式数据库。
- API 费用和网络稳定性影响使用体验。
- 录音隐私和客户敏感信息需要明确告知。

控制措施：

- 强制人工确认。
- 字段保留来源片段。
- 未知字段显式标记。
- 低可信字段突出显示。
- 必填未知时禁止直接入库。
- 首版先限制单次处理一段录音。

## 17. 推荐开发拆分

### 17.1 内部验证版本

- 支持粘贴文字稿。
- 调用大模型抽取草稿。
- 展示未知字段。
- 不接入音频上传。

目标：验证字段映射和草稿确认流程。

### 17.2 第一版 MVP

- 支持上传录音。
- 联网转文字。
- 联网抽取结构化草稿。
- 支持人工确认入库。

目标：满足真实销售拜访后录入场景。

### 17.3 第二版增强

- 支持本地转写方案评估。
- 支持说话人分离。
- 支持从草稿生成待办提醒。
- 支持批量处理多段录音。

## 18. 当前决策建议

建议下一步先开发“文字稿智能抽取草稿”内部验证版本，而不是直接处理录音。

理由：

- 可以先验证最核心的结构化抽取能力。
- 可以更早发现字段设计和确认流程问题。
- 之后接入语音转文字时，整体风险更小。

如果要直接做录音版本，也建议保留“粘贴文字稿”入口，方便调试和处理第三方转写结果。
